# Security

## What runs where

- The gateway runs inside an **AWS Nitro enclave**: no disk, no shell, no network except a fixed egress allowlist (KMS, DynamoDB for sealed records, the instance metadata service for AWS credentials, the provider APIs, the control plane).
- **TLS ends inside the enclave.** Caddy runs in the enclave image next to the gateway, so the parent host only forwards encrypted bytes and never sees a key in transit. The certificate's private key and Caddy's state are sealed with the KMS key, so the host never holds them either.
- The KMS key policy denies `kms:Decrypt` to everyone, account admins included, unless the request carries an attestation document whose image hash (`PCR0`) matches the enclave image you deployed. It denies `kms:ReEncrypt*` to everyone, so a stored share cannot be moved under another key and opened there.

## Verify the enclave

**The SDK does this for you.** Set `FIDUCY_ENCLAVE_PCR0` on your app server to the `PCR0` your deploy printed. Before the widget shows the key box, the user's browser asks the gateway for a fresh attestation and checks it with WebCrypto; `importKeys` does the same on your server before it sends any key. If the check fails, nothing is sent and the widget says why.

The check refuses: a document not signed through the AWS Nitro root, a document made for another request (nonce), an enclave in debug mode, and an enclave running any image other than the `PCR0`s you listed. During an upgrade, list both values separated by a comma, then drop the old one.

Gateways on `localhost` (such as `npx fiducy dev`) are not checked. A test gateway that is not in an enclave needs `FIDUCY_SKIP_ATTESTATION=true`; the browser console warns every time. Any other gateway with neither variable set is refused.

The `PCR0` must come from your deploy output (or a release you trust), never from the gateway you are checking.

To check by hand:

```bash
curl "https://gateway.yourapp.com/attestation?nonce=$(openssl rand -hex 16)"
```

The response holds a CBOR attestation document signed by AWS. Check that:

1. the certificate chain ends at the AWS Nitro root certificate,
2. your nonce is in the document,
3. `PCR0` equals the hash your deploy printed and locked the KMS key to.

Today the enclave image is built on your host during the deploy, so `PCR0` identifies the image you built, not a build published by Fiducy, and two builds of the same source can differ. Reproducible builds with a published `PCR0` and a `fiducy verify` command are planned. You can also check a document in code with `verifyNitroAttestation` from `@fiducy/core/attestation`.

## What it protects against

| Threat | Result |
| --- | --- |
| Your database leaks | Attacker gets handles. Useless without the enclave and your app secret |
| Fiducy's storage leaks | Attacker gets records. Useless without the handles |
| Your server logs leak | Only handles and the app secret appear; rotate the secret |
| Someone with AWS admin on the gateway account | Cannot decrypt stored keys through KMS: it refuses `Decrypt` without the enclave's attestation and refuses `ReEncrypt` always. An admin can still rewrite the key policy, which shows in CloudTrail as `PutKeyPolicy`; watch for it |

## Limits

- **Your app secret plus a handle can use a key** through the gateway. Monthly limits per key cap the damage; rotate the secret if it leaks.
- **No plaintext comes back.** There is no endpoint that returns a stored key to your server. The gateway proxy is the only way to use one; ask for a provider the proxy does not cover.
- **The provider sees the key**, as it always does.
- **The attestation check trusts TLS for the hostname.** It proves an approved enclave answered `/attestation`. Someone who controls the gateway's host and can also get a certificate for its hostname could relay that answer from the real enclave while serving a fake key box. Lock certificate issuance to the enclave with CAA and watch Certificate Transparency logs for your hostname.
- **Hosting**: a flaw in Nitro or KMS would break the guarantees. Self-hosting moves that trust to your own account.
