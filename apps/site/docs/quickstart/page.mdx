# Quickstart

This guide adds Fiducy to an app you already have. It works with any server that handles a standard Web `Request` (Next.js, Hono, React Router, SvelteKit, Farm.js, Bun, Deno and others), any auth with a server session, and any way of calling the model.

You add four things:

1. a server module that knows your gateway, your storage and your signed-in user
2. one route that saves and lists each user's key handles
3. the key widget, where users paste their key
4. a model call that uses the user's key through the gateway

**Before you start:** your app needs sign-in. Fiducy stores each key for a signed-in user, so set up auth first if you don't have it ([Better Auth](https://www.better-auth.com), [Auth.js](https://authjs.dev), [Clerk](https://clerk.com) or any auth with a server session).

Install the SDK:

```bash
npm install @fiducy/sdk
```

Using Farm.js or assistant-ui? Follow this guide, then the [Farm.js](/docs/farm) or [assistant-ui](/docs/assistant-ui) page for the shortcuts they add.

## 0. Have a gateway to talk to

Your app needs a running Fiducy gateway and dashboard. Two options:

| Option | Dashboard | Gateway URL |
| --- | --- | --- |
| Local, for trying it out | `http://localhost:3000` | `http://localhost:8787` |
| Your own deployment | Wherever you host it | Its public URL, for example `https://gateway.yourapp.com` |

For the local option, clone the [Fiducy repo](https://github.com/fiducy-dev/fiducy) and run `bun install && bun run prototype --mock`; see [Self-hosting](/docs/self-hosting#run-locally). It takes ports 3000, 3001 and 8787, so run your own app on another port, for example 5173.

## 1. Register your app

Sign up in the Fiducy dashboard and create an app. You get:

- an **app ID**, public, used by the widget
- an **app secret** (`fsk_...`), server only, used for every gateway call

Add your site's origin to the app's allowed origins, so the widget can be embedded there. Use the exact scheme, host and port, for example `http://localhost:5173` while developing and `https://myapp.com` in production.

Put the values in your server's environment (keep `.env` out of git):

```bash
FIDUCY_GATEWAY_URL=http://localhost:8787
FIDUCY_APP_ID=app_...
FIDUCY_APP_SECRET=fsk_...
```

Never give the app secret a client-exposed prefix such as `NEXT_PUBLIC_` or `VITE_`. Only the app ID and gateway URL may reach the browser. The widget in step 4 needs those two: either pass them down from server code as props, or add public copies such as `NEXT_PUBLIC_FIDUCY_APP_ID` and `NEXT_PUBLIC_FIDUCY_GATEWAY_URL`.

## 2. Create the server module

Create the Fiducy instance once, in a file only server code imports:

```ts title="lib/fiducy.ts"
import { createFiducy, keyValueStorage } from '@fiducy/sdk/server';

import { getSessionUserID } from './auth'; // your auth
import { kv } from './kv'; // your storage

const { FIDUCY_GATEWAY_URL, FIDUCY_APP_SECRET } = process.env;
if (!FIDUCY_GATEWAY_URL || !FIDUCY_APP_SECRET) throw new Error('Set the Fiducy env vars');

export async function getUserID(request: Request) {
  return (await getSessionUserID(request)) ?? null;
}

export const fiducy = createFiducy({
  gatewayURL: FIDUCY_GATEWAY_URL,
  appSecret: FIDUCY_APP_SECRET,
  storage: keyValueStorage(kv),
  getUserID
});
```

The check at the top throws the first time the module loads. Build tools that load routes at build time (`next build`, for example) need the env vars at build time too.

**`getUserID`** tells Fiducy who is asking. Read the user from your auth's server session and return `null` when nobody is signed in. Never take the ID from the request body, the query or a header the browser sets. For example:

| Auth | `getUserID` body |
| --- | --- |
| Better Auth | `(await auth.api.getSession({ headers: request.headers }))?.user.id` |
| Auth.js | `(await auth())?.user?.id` |
| Clerk (Next.js) | `(await auth()).userId` |
| Supabase | `(await supabase.auth.getUser()).data.user?.id` |
| Farm Auth | `(await auth.user({ request }))?.id` |

**`storage`** is where your app keeps each user's key handle (a reference to the sealed key, never the key). `keyValueStorage` takes any [unstorage](https://unstorage.unjs.io) instance (Redis, Postgres, Cloudflare KV, the file system and more), or you can write four methods against your own database table. See [Storage](/docs/storage). In production, use storage that survives restarts; `memoryStorage()` is for tests only.

### No auth or storage yet?

A fresh template (for example `npx assistant-ui create`) has neither.

**Storage:** unstorage's file driver keeps handles on disk:

```bash
npm install unstorage
```

```ts title="lib/kv.ts"
import { createStorage } from 'unstorage';
import fsDriver from 'unstorage/drivers/fs';

export const kv = createStorage({ driver: fsDriver({ base: '.data/fiducy' }) });
```

Add `.data/` to `.gitignore`. This works locally and on a long-running server. Serverless hosts such as Vercel wipe the disk, so there, switch the driver to Upstash, Vercel KV or Redis; nothing else changes.

**Auth:** set it up first (see the top of this page), then come back to `getUserID`.

## 3. Mount the key route

`fiducy.handler` is a standard `Request => Response` handler. Mount it for `GET`, `POST` and `DELETE` under `/api/fiducy`:

```ts title="Next.js: app/api/fiducy/[...path]/route.ts"
import { fiducy } from '@/lib/fiducy';

export const GET = fiducy.handler;
export const POST = fiducy.handler;
export const DELETE = fiducy.handler;
```

```ts title="Hono"
app.all('/api/fiducy/*', (c) => fiducy.handler(c.req.raw));
```

```ts title="React Router / Remix: app/routes/api.fiducy.$.ts"
import { fiducy } from '~/lib/fiducy.server';

export const loader = ({ request }: { request: Request }) => fiducy.handler(request);
export const action = ({ request }: { request: Request }) => fiducy.handler(request);
```

```ts title="SvelteKit: src/routes/api/fiducy/[...path]/+server.ts"
import { fiducy } from '$lib/server/fiducy';

const handle = ({ request }: { request: Request }) => fiducy.handler(request);
export { handle as GET, handle as POST, handle as DELETE };
```

Farm.js mounts it for you through `@fiducy/farm`; see [Farm.js](/docs/farm). Frameworks built on Node's `req`/`res` (Express, Fastify) need a small adapter that turns the request into a Web `Request`, such as `@whatwg-node/server`.

You get `GET /api/fiducy/keys`, `POST /api/fiducy/keys` and `DELETE /api/fiducy/keys/:keyID`. They answer `401` when signed out and `403` for cross-site writes.

## 4. Add the key widget

The widget is an iframe served by your gateway. The key goes straight from the user's browser into it, and your page only gets back a handle, which it saves through the route from step 3.

**React:**

```tsx title="components/ConnectOpenAIKey.tsx"
'use client';

import { ConnectKeyWidget } from '@fiducy/sdk/react';
import { useState } from 'react';

export function ConnectOpenAIKey() {
  const [connected, setConnected] = useState(false);

  if (connected) return <p>Your OpenAI key is connected.</p>;
  return (
    <ConnectKeyWidget
      gatewayURL="http://localhost:8787" // your FIDUCY_GATEWAY_URL
      appID="app_..." // your FIDUCY_APP_ID
      provider="openai"
      onConnected={() => setConnected(true)}
    />
  );
}
```

**Any other framework** (Vue, Svelte, Solid, plain HTML) uses `@fiducy/widget` and one `fetch`:

```ts
import { mountKeyWidget } from '@fiducy/widget';

mountKeyWidget({
  gatewayURL: 'http://localhost:8787',
  appID: 'app_...',
  container: document.getElementById('key-box')!,
  onHandle: async (handle, record) => {
    await fetch('/api/fiducy/keys', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ provider: 'openai', handle, record })
    });
  }
});
```

Put the widget on a settings page, or wherever users first need a key. To list and remove saved keys, call `GET /api/fiducy/keys` and `DELETE /api/fiducy/keys/:keyID`. See [React](/docs/react) for the list helpers.

## 5. Call the model with the user's key

`fiducy.providerSettings(provider, { userID })` returns `{ baseURL, apiKey, headers }` pointing at your gateway, or `null` when the user has no key for that provider. Pass it to whatever you call the model with. When it is `null`, ask the user to connect a key; never fall back to a key of your own.

With the [AI SDK](https://ai-sdk.dev):

```ts title="app/api/chat/route.ts"
import { createOpenAI } from '@ai-sdk/openai';
import { streamText } from 'ai';

import { fiducy, getUserID } from '@/lib/fiducy';

export async function POST(request: Request) {
  const userID = await getUserID(request);
  const settings = userID ? await fiducy.providerSettings('openai', { userID }) : null;
  if (!settings) return new Response('Connect your API key first', { status: 400 });

  const { messages } = await request.json();
  const result = streamText({ model: createOpenAI(settings).chat('gpt-4o-mini'), messages });
  return result.toUIMessageStreamResponse();
}
```

With the official OpenAI SDK (also works for `openrouter`):

```ts
import OpenAI from 'openai';

const { baseURL, apiKey, headers } = settings;
const openai = new OpenAI({ baseURL, apiKey, defaultHeaders: headers });
```

With plain `fetch`:

```ts
const { baseURL, apiKey, headers } = settings;
const response = await fetch(`${baseURL}/chat/completions`, {
  method: 'POST',
  headers: { ...headers, authorization: `Bearer ${apiKey}`, 'content-type': 'application/json' },
  body: JSON.stringify({ model: 'gpt-4o-mini', messages })
});
```

For Anthropic, the AI SDK's `createAnthropic(settings)` works as is. The official Anthropic SDK adds `/v1` itself, so give it `baseURL.replace(/\/v1$/, '')`.

## 6. Try it

1. Sign in to your app, open the page with the widget, paste a key and save. With `--mock`, any string works, for example `sk-test-1234`.
2. The page shows that the key is connected.
3. Send a chat request. With `--mock`, the prototype's terminal logs `[fake OpenAI] ... received the decrypted key ...1234`.

If the chat route answers "Connect your API key first" right after you connected one, check `getUserID` (same user in both routes?) and your storage.

That is the whole integration. The plaintext key only ever exists inside the gateway.
